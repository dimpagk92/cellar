## Scope B — Adapter trait reconciliation (`Adapter` vs `AdapterDriver`)

**Why**: Two parallel public traits today. [adapters/adapter-common/src/lib.rs](../adapters/adapter-common/src/lib.rs) defines `Adapter` (info / is_available / connect / execute_action) — what `excel`, `bloomberg`, etc. implement. [cel/cel-cortex/src/adapter.rs](../cel/cel-cortex/src/adapter.rs) defines `AdapterDriver` (manifest / activate / deactivate / get_context / execute / probe / snapshot) — what `browser` and `numbers` implement, what Cortex actually consumes via `register_adapter`. The recently-extracted `adapter-numbers` crate had to depend on `cel-cortex` for the trait, breaking the convention `excel` etc. follow. [docs/adapter-sdk.md](adapter-sdk.md) flags this as v1 SDK work.

**Acceptance:**
- One public trait surface in `adapter-common` consumed by Cortex.
- All five `adapters/*` crates depend on `adapter-common` only — none depend on `cel-cortex`.
- `adapter-common` documents v1 stability commitments per [docs/stability.md](stability.md).
- All existing first-party adapters compile + their tests pass.
- Migration note added to [docs/building-adapters.md](building-adapters.md).

**Suggested first move:** decide which trait shape wins (the AdapterDriver shape is richer, used by the only production adapter — recommend that one). Move it from `cel-cortex/src/adapter.rs` into `adapter-common`. Make `cel-cortex` re-export from there for backcompat. Refactor existing adapters one at a time.

**Estimate:** 1-2 days. Touches public API surface — high blast radius, low complexity per file.
